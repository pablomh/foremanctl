# Certificate Management

This document describes how certificate generation and management works in foremanctl.

## User Guide

### Certificate Sources

foremanctl supports two certificate sources that determine how certificates are obtained:

**Default Source (`certificate_source: default`)**
- Automatically generates self-signed certificates during deployment
- Creates a complete PKI infrastructure with CA, server, and client certificates
- Recommended for development and testing environments

**Custom Server Source (`certificate_source: custom_server`)**
- Uses custom server certificates provided by the user (e.g., signed by your organization's CA)
- Automatically generates an internal CA for client certificates and localhost
- Server certificate, key, and CA bundle are copied to `/var/lib/foremanctl/certs/`
- Certificate source persists across deployments; original files only needed on first deploy or when updating certificates

### Usage

#### Using Auto-Generated Certificates (Default)

```bash
# Deploy with auto-generated certificates
foremanctl deploy

# Explicitly specify default certificate source
foremanctl deploy --certificate-source=default
```

#### Using Custom Server Certificates

```bash
# First deployment with custom certificates
foremanctl deploy \
  --certificate-source=custom_server \
  --certificate-server-certificate /path/to/server.crt \
  --certificate-server-key /path/to/server.key \
  --certificate-server-ca-certificate /path/to/ca-bundle.crt

# Subsequent deployments (certificate paths no longer needed)
foremanctl deploy

# Update certificates (provide new paths)
foremanctl deploy \
  --certificate-server-certificate /new/path/server.crt \
  --certificate-server-key /new/path/server.key \
  --certificate-server-ca-certificate /new/path/ca-bundle.crt

# Switch back to auto-generated certificates
foremanctl deploy --certificate-source=default
```

#### Migrating from foreman-installer

When migrating from a `foreman-installer` deployment, use the `migrate` command to normalize existing certificates into foremanctl's canonical structure:

```bash
foremanctl migrate --apply
foremanctl deploy
```

The `migrate --apply` command copies certificates from `/root/ssl-build/` into `/var/lib/foremanctl/certs/`, persists the CA passphrase so foremanctl can issue new certificates, and backs up the original directory to `/root/ssl-build.bak/`. Run `foremanctl migrate` without `--apply` to preview the migration first. See the [migration guide](../migration-guide.md) for full details.

### Certificate Locations

With exactly one algorithm enabled (`--add-certificate-algorithm` passed once, or not at all with a single-entry default), certificates use flat filenames:

**Default Source:**
- CA Certificate: `/var/lib/foremanctl/certs/certs/ca.crt`
- Server Certificate: `/var/lib/foremanctl/certs/certs/<hostname>.crt`
- Client Certificate: `/var/lib/foremanctl/certs/certs/<hostname>-client.crt`

**Custom Server Source:**
- CA Certificate: `/var/lib/foremanctl/certs/certs/ca.crt` (internal CA)
- Server Certificate: `/var/lib/foremanctl/certs/certs/<hostname>.crt` (custom, user-provided)
- Server CA Certificate: `/var/lib/foremanctl/certs/certs/server-ca.crt` (custom CA that signed server cert)
- Client Certificate: `/var/lib/foremanctl/certs/certs/<hostname>-client.crt` (generated by internal CA)

With more than one algorithm enabled (the default), each one gets a type-suffixed name instead (`rsa`, `ecc`, `mldsa65`, `mldsa87`):
- CA Certificate: `/var/lib/foremanctl/certs/certs/<type>-ca.crt` (one per enabled algorithm)
- Internal CA bundle (all enabled CAs, no external CA): `/var/lib/foremanctl/certs/certs/internal-ca-bundle.crt`
- Full CA bundle (adds the external CA in custom-server mode): `/var/lib/foremanctl/certs/certs/ca-bundle.crt`
- Server Certificate: `/var/lib/foremanctl/certs/certs/<hostname>-<type>.crt` (one per enabled algorithm; the custom cert, if any, fills the primary algorithm's slot)
- Independent client certificate for internal links (foreman-proxy, iop-core-gateway), always one algorithm regardless of the server list: `/var/lib/foremanctl/certs/certs/<identity>-client-<type>.crt`

The flat `ca.crt`/`<hostname>.crt` names only exist with exactly one enabled algorithm; consumers that need "the" CA or server cert regardless of mode (`ca_certificate`, `server_certificate`) resolve to the matching type-suffixed file automatically when multiple algorithms are enabled.

**After Migration:**
- Certificates from `foreman-installer` are normalized into the same paths as the Default Source above
- Original directory is backed up to `/root/ssl-build.bak/`

**Proxy/Secondary System Certificates (from auth-bundle):**
- Generated in per-host subdirectories: `/var/lib/foremanctl/certs/hosts/<hostname>/`
- Packaged tarball: `/var/lib/foremanctl/certs/bundles/<hostname>.tar.gz`

### Server aliases

foremanctl supports Subject Alternative Names (SANs) for multi-domain certificates. `--server-alias` is available both on `deploy` (for the main Foreman server) and on `auth-bundle` (for secondary systems such as a foreman-proxy host):

```bash
# Generate certificates with multiple DNS names
foremanctl deploy \
  --server-alias api.example.com \
  --server-alias foreman.example.com \
  --server-alias satellite.example.com
```

When server aliases are specified, certificates will include all names in the Subject Alternative Name field, allowing the same certificate to be valid for multiple hostnames.

If certificates already exist from a previous deployment, passing `--server-alias` will automatically regenerate the server certificate and CSR to include the new aliases. Existing private keys are reused.

To remove all aliases from an existing certificate, use `--reset-server-alias`.

On each run the role compares the Subject Alternative Names in the existing server certificate against the desired list (hostname + any `--server-alias` values). If they differ, the CSR and certificate are regenerated automatically. This means both adding and removing aliases are handled transparently without manual cleanup.

### Validity period

When certificates are generated by foremanctl, you can control lifetimes in days:

| CLI flag | Ansible variable | What it controls |
| -------- | ---------------- | ---------------- |
| `--certificate-ca-validity-days` | `certificates_ca_validity_days` | Lifetime of the CA certificate (`ca.crt`) |
| `--certificate-validity-days` | `certificates_validity_days` | Lifetime of server and client certificates issued for each hostname |

Defaults: both are 7300 days (about 20 years).

### Key algorithm

`--add-certificate-algorithm` may be specified more than once (default: `RSA` and `ML-DSA-65`). Each algorithm gets its own CA and its own server certificate per hostname, so Apache/Candlepin/the IOP gateway can present a dual-cert handshake and clients negotiate whichever algorithm their TLS stack supports. With exactly one algorithm enabled, foremanctl falls back to the original single-CA, flat-filename layout (see [Certificate Locations](#certificate-locations)).

The first entry in `--add-certificate-algorithm` is the **primary algorithm** (`certificates_primary_algorithm`): it's the one used for the custom-server certificate check, the CA-key-mismatch guard, and as the "legacy" Candlepin crypto scheme when RSA isn't one of the enabled algorithms.

| CLI flag | Ansible variable | What it controls |
| -------- | ---------------- | ---------------- |
| `--add-certificate-algorithm` | `certificates_algorithms` | Key algorithm(s): `RSA`, `ECC`, `ML-DSA-65` or `ML-DSA-87`, repeatable. Defaults to `RSA` and `ML-DSA-65`. |
| `--certificate-algorithm-rsa-size` | `certificates_algorithm_rsa_size` | Key size, RSA only (default 4096) |
| `--certificate-algorithm-ecc-curve` | `certificates_algorithm_ecc_curve` | Elliptic curve, ECC only (default `secp384r1`) |
| `--certificate-client-algorithm` | `certificates_client_algorithm_type` | Key algorithm for the independent client certificate used on internal links (foreman-proxy-to-Foreman, iop-core-gateway-to-Foreman). Independent of `--add-certificate-algorithm`. Defaults to `ML-DSA-65`. |

```bash
# Default: dual-cert with RSA and ML-DSA-65
foremanctl deploy

# Single algorithm: ECC only, on a non-default curve
foremanctl deploy --add-certificate-algorithm=ECC --certificate-algorithm-ecc-curve=secp521r1

# Dual-cert with RSA and ECC instead of the default pair
foremanctl deploy --add-certificate-algorithm=RSA --add-certificate-algorithm=ECC
```

Server and client (leaf) certificates with non-RSA keys only carry the `digitalSignature` key usage, because those keys cannot perform key encipherment. RSA leaf certificates keep both `digitalSignature` and `keyEncipherment`. The CA certificate is signed for `keyCertSign`, `cRLSign` and `digitalSignature` regardless of the algorithm, since those usages do not depend on key encipherment.

> [!NOTE]
> ML-DSA algorithms need `community.crypto` 3.3.0 to generate the keys and `python-cryptography` 49.0.0 to sign certificates and CSRs with them. CentOS Stream 10 ships a suitable `python-cryptography`; CentOS Stream 9 ships 36.0.1, on which selecting an ML-DSA algorithm fails at key generation.

> [!NOTE]
> `ML-DSA-87`'s certificate chain can exceed some TLS stacks' handshake buffers (notably Tomcat, used by Candlepin), stalling the connection. `ML-DSA-65` is the default PQC algorithm until that's fixed upstream.

Changing `--add-certificate-algorithm` on an existing deployment re-issues the server and client (leaf) certificates automatically: their keys are regenerated with the new algorithm and re-signed by the matching CA, no `--certificate-renew` needed. Existing CAs are never changed silently; adding a new algorithm generates a new CA for it alongside the existing ones. If an already-enabled algorithm's CA key no longer matches what was requested (single-algorithm mode only), the deploy fails and asks you to pass `--certificate-ca-renew`, which reissues the CA and every certificate it signed with the new algorithm.

### Renewing certificates

To re-issue server and client certificates that foremanctl generated earlier, while keeping the same CA (`ca.crt` and CA key), use:

```bash
foremanctl deploy --certificate-renew
```

To regenerate the CA certificate itself, use:

```bash
foremanctl deploy --certificate-ca-renew
```

> [!WARNING]
> Regenerating the CA invalidates all previously issued certificates. Does not apply to custom certificates.

Both flags are **not persisted** in foremanctl’s answers file (one-shot).

### Auth Bundle for Secondary Systems

The `auth-bundle` command generates a certificate and OAuth credential tarball for a secondary system such as a foreman-proxy host. This is the foremanctl equivalent of `foreman-proxy-certs-generate`.

The internal CA must already exist from a prior `foremanctl deploy`.

#### Usage

```bash
# Generate an auth bundle using the internal CA
foremanctl auth-bundle proxy.example.com

# Generate an auth bundle with custom server certificates for the proxy
foremanctl auth-bundle \
  --certificate-server-certificate /path/to/proxy.example.com.crt \
  --certificate-server-key /path/to/proxy.example.com.key \
  proxy.example.com
```

The command generates certificates for the given hostname and packages them into a tarball at `/var/lib/foremanctl/certs/bundles/<hostname>.tar.gz`.

When no custom certificate flags are provided, all certificates (server and client) are generated by the internal CA. When custom server certificates are provided, the custom cert and key are used for the proxy's server certificates while client certificates are still generated by the internal CA. The server CA certificate is always taken from the canonical location established during `foremanctl deploy`.

If the Foreman server was deployed with custom server certificates, each proxy must also have its own distinct custom server certificate. The `--certificate-server-certificate` and `--certificate-server-key` flags are required when `--certificate-source=custom_server`.

#### Load-balanced proxies

When a proxy sits behind a load balancer that does TLS passthrough (the load balancer forwards TCP traffic without terminating TLS itself), the proxy's own certificate is what clients validate, so it must carry the load balancer's FQDN as a SAN. Use `--server-alias` when generating the auth bundle:

```bash
foremanctl auth-bundle --server-alias loadbalancer.example.com proxy.example.com
```

Combine this with `--registration-url` and `--templates-url` on `deploy-proxy` (pointed at the load balancer) to complete the load-balanced proxy setup. `--server-alias` only applies when certificates are issued by the internal CA (see [Current Limitations](#current-limitations)).

#### Tarball Contents

The tarball mirrors the on-disk layout under `/var/lib/foremanctl/`:

```
certs/
├── ca.crt                           # Internal CA certificate (its basename, e.g. rsa-ca.crt with multiple algorithms)
├── server-ca.crt                    # CA that signed the server certificate, if different from ca.crt
├── <hostname>.crt                   # Server certificate
├── <hostname>-<type>.crt            # Per-algorithm server certificate (one per enabled algorithm beyond the first)
└── <hostname>-client-<type>.crt     # Independent client certificate for internal links
private/
├── <hostname>.key                   # Server private key
├── <hostname>-<type>.key            # Per-algorithm server private key
└── <hostname>-client-<type>.key     # Independent client private key
oauth/
├── foreman-oauth-consumer-key      # OAuth consumer key for Foreman API auth
└── foreman-oauth-consumer-secret   # OAuth consumer secret for Foreman API auth
```

On extract, `certs/` and `private/` are installed under `/var/lib/foremanctl/certs/`, and `oauth/` is installed under `/var/lib/foremanctl/oauth/`.

When using the internal CA only, `server-ca.crt` and `ca.crt` are identical. When custom server certificates are provided, `server-ca.crt` contains the custom CA and `ca.crt` contains the internal CA.

### Current Limitations

- Uses the same lifetime for both client and server certificates
- Limited certificate customization options
- Server aliases (`--server-alias`) are only applied to certificates generated by the internal CA

## Internal Design

### Architecture

The certificate system uses a modular Ansible role-based approach with clear separation between generation, validation, and usage phases.

#### Certificate Role Structure

```
src/roles/certificates/
├── tasks/
│   ├── main.yml                         # Entry point for certificate management
│   ├── ca.yml                           # Primary/single-algorithm CA generation + migration
│   ├── ca-algorithm.yml                 # Per-algorithm CA generation (multi-scheme)
│   ├── host.yml                         # Per-hostname entry point (custom/issue/per-algorithm)
│   ├── issue.yml                        # Primary/single-algorithm server+client issuance
│   ├── issue-algorithm.yml              # Per-algorithm server certificate issuance (multi-scheme)
│   ├── independent_client_certificate.yml  # Client cert for internal links, own algorithm
│   └── custom.yml                       # Applies user-provided custom server certs
├── defaults/main.yml          # Default configuration variables
└── vars/<algorithm>.yml       # Per-algorithm key parameters and key usage, one file per algorithm

src/roles/auth_bundle/
├── tasks/main.yml             # Packages certificates into a tarball
└── defaults/main.yml          # Output directory configuration
```

#### Certificate Generation Workflow

For `certificate_source: default`:

1. **CA Generation** (when `certificates_ca: true`):
   - Install dependencies (`python3-cryptography`) and create directory layout under `certificates_ca_directory`
   - With one enabled algorithm: generate a single CA private key (`certificates_primary_algorithm`, default `RSA` 4096) and self-signed CA certificate (`CN: Foreman Self-signed CA`)
   - With more than one enabled algorithm (the default): generate one CA key/certificate per `certificates_enabled_algorithms` entry (`ca-algorithm.yml`), then assemble `internal-ca-bundle.crt` from all of them
   - Not-after for every CA comes from `certificates_ca_validity_days`

2. **Host Certificate Issuance** (for each hostname in `certificates_hostnames`):
   - Generate server key and CSR with SANs (hostname plus `certificates_server_aliases`) and the key usage matching the algorithm
   - Sign server certificate with the matching CA (`ownca_not_after` from `certificates_validity_days`; `force` when `certificates_renew`); with more than one enabled algorithm, this repeats per algorithm (`issue-algorithm.yml`) producing `<hostname>-<type>.crt`
   - Generate client key and CSR, sign client certificate the same way, for hostnames in `certificates_client_hostnames`
   - Foreman-proxy and iop-core-gateway additionally get an independent client certificate under `certificates_client_algorithm_type`, regardless of the server algorithm list (`independent_client_certificate.yml`)

Generation uses **`community.crypto`** (keys, CSRs, X.509) and **`python3-cryptography`**.

For `certificate_source: custom_server`:

1. **CA Generation**: Generate self-signed internal CA certificate(s) and key(s) with 20-year validity, one per enabled algorithm
2. **Custom Server Certificates**: Copy the custom server cert, key, and CA bundle from user-provided paths to `/var/lib/foremanctl/certs/` (only when certificate paths are provided); the custom cert's algorithm must match `certificates_primary_algorithm`. With more than one algorithm enabled, the custom cert is also copied under the primary algorithm's type-suffixed name, since that's what httpd/Candlepin/the IOP gateway read.
3. **Host Certificate Issuance**: Generate client certificates for every hostname. Internally issued server certificates are still created for localhost and other internal names (`candlepin`, `iop-core-gateway`). For the public FQDN, the primary algorithm's server certificate is skipped (the custom cert fills that slot instead); any other enabled algorithms still get an internally-issued server certificate for the public FQDN.

#### Auth Bundle Generation

The `auth-bundle` playbook reuses the `certificates` role to generate proxy certificates in a per-host subdirectory (`certificates_ca_directory/hosts/<hostname>/`). It overrides `certificates_ca_directory_certs`, `certificates_ca_directory_keys`, and `certificates_ca_directory_requests` to point to the subdirectory while keeping `certificates_ca_directory` unchanged so the CA can still be found for signing. It sets `certificates_ca: false` (the CA already exists from a prior deploy) and passes the proxy hostname via `certificates_hostnames`. The `auth_bundle` role then packages the generated certificates along with the CA into a tarball under `certificates_ca_directory/bundles/`.

When custom server certificates are provided for the proxy, `certificates_source` is set to `custom_server` so only client certificates are generated by the internal CA. The custom server certificate, key, and CA are validated by the `certificate_checks` role and then packaged directly into the tarball by the `auth_bundle` role.

#### Migration from foreman-installer

The `foremanctl migrate --apply` command includes a `migrate_foreman_installer` role that normalizes `foreman-installer` certificates into the canonical `/var/lib/foremanctl/certs/` structure. It also reads the CA passphrase from the installer's password file and persists it into foremanctl's configuration so that subsequent deploys can issue new certificates using the original CA.

#### Variable System

Certificate paths are defined in `src/vars/certificates.yml`. `ca_certificate`/`ca_key` resolve to either the flat name or the primary algorithm's type-suffixed name depending on how many algorithms are enabled:

```yaml
ca_certificate: "{% if certificates_enabled_algorithms | length == 1 %}.../ca.crt{% else %}.../<type>-ca.crt{% endif %}"
internal_ca_bundle: "{{ certificates_ca_directory }}/certs/internal-ca-bundle.crt"
ca_bundle: "{% if certificates_source == 'custom_server' %}.../ca-bundle.crt{% else %}{{ internal_ca_bundle }}{% endif %}"
server_certificate: "{{ certificates_ca_directory }}/certs/{{ ansible_facts['fqdn'] }}.crt"
server_ca_certificate: "{% if certificates_source == 'custom_server' %}.../server-ca.crt{% else %}{{ ca_certificate }}{% endif %}"
client_certificate: "{{ certificates_ca_directory }}/certs/{{ ansible_facts['fqdn'] }}-client.crt"
client_ca_certificate: "{{ internal_ca_bundle }}"
```

`internal_ca_bundle` and `ca_bundle` serve different trust purposes and must not be used interchangeably: `internal_ca_bundle` contains only internally-issued CAs and is what anything *verifying an incoming client certificate* should trust (httpd's `SSLCACertificateFile`, Candlepin's and foreman-proxy's client-auth trust store), since client certificates are always internally signed. `ca_bundle` additionally includes the external CA in custom-server mode and is for verifying *this server's own* certificate from the outside (what Foreman's proxies/Pulp/hammer trust when connecting to Foreman). Conflating the two would make Apache/Candlepin/foreman-proxy accept client certificates signed by an unrelated external CA.

`server_certificate`/`client_certificate` always point at the flat name; in multi-scheme mode, httpd/Candlepin/the IOP gateway instead read the type-suffixed `<hostname>-<type>.crt` files directly (`certificates_output_directory_certs`), and internal links read `<identity>-client-<type>.crt` from `independent_client_certificate.yml`.

#### Integration with Deployment

In `src/playbooks/deploy/deploy.yaml`:

1. **Variable Loading**: Loads certificate variables from `src/vars/certificates.yml`
2. **Certificate Generation**: Runs `certificates` role when `certificate_source == 'default'`
3. **Certificate Validation**: Runs `certificate_checks` role for all sources
4. **Service Configuration**: Passes certificate paths to dependent roles

#### Validation System

The `certificate_checks` role uses `foreman-certificate-check` binary to validate:
- Certificate file existence and readability
- PEM format validation
- Private key and certificate pairing
- Certificate chain integrity
- Key usage appropriate for the certificate's key algorithm: Key Encipherment for RSA, Digital Signature for EC and ML-DSA
- No SHA-1 in the signature algorithm of any certificate in the CA bundle, whichever key type signed it

### Technical Specifications

**Certificate Properties:**
- Key algorithm(s): `RSA` 4096 and `ML-DSA-65` by default (`certificates_enabled_algorithms`, first entry is `certificates_primary_algorithm`); `ECC` uses `certificates_algorithm_ecc_curve`
- Hash Algorithm: SHA256 (via `community.crypto` defaults)
- Validity:
  - CA: `certificates_ca_validity_days` (default 7300 days)
  - Server and client certificates: `certificates_validity_days` (default 7300 days)
- Extensions: serverAuth / clientAuth as appropriate for server and client certificates
- Key usage: leaf certificates carry `digitalSignature`, plus `keyEncipherment` for RSA only; the CA certificate carries `keyCertSign`, `cRLSign` and `digitalSignature` for every algorithm

**Directory Structure:**
```
/var/lib/foremanctl/certs/
├── certs/           # Public certificates (CA, server, client)
├── private/         # Private keys and passwords
├── requests/        # Certificate signing requests
├── bundles/         # Certificate tarballs for secondary systems
└── hosts/           # Per-host proxy certificate directories
    └── <hostname>/
        ├── certs/
        ├── private/
        └── requests/
```

**SANs and server aliases:**
- Server SANs are built in Ansible (`openssl_csr`) from the hostname and optional `certificates_server_aliases` (from `--server-alias`).
- Client CSR uses a SAN entry for the hostname being issued.
